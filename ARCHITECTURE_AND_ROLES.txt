1. EXECUTIVE OVERVIEW & PLATFORM PURPOSE
================================================================================
UpVolt Manager is an enterprise-grade ERP and inventory management SaaS tailored 
for hardware businesses, IoT component distributors, and collegiate engineering 
supply chains.

Key Capabilities:
  - Real-time hardware catalog management with dual SKU & barcode tracking.
  - Strict First-In, First-Out (FIFO) batch-layer costing and COGS computation.
  - Multi-tier inventory hierarchy (Central Warehouse -> College Campus Hubs).
  - Commercial order processing with automatic stock reservation and versioning.
  - Granular Role-Based Access Control (RBAC) enforcing business privileges.
  - Complete, tamper-evident audit logging for regulatory & financial trace.

================================================================================

  1. MASTER_ADMIN      : Complete administrative, financial, and destructive power.
  2. STAFF             : Central operations, purchasing, and order fulfillment.
  3. COLLEGE_MEMBER    : College campus lead; isolated to their assigned college stock.

================================================================================
4. DETAILED ROLE CAPABILITIES & RESTRICTIONS
================================================================================

--------------------------------------------------------------------------------
4.1 MASTER_ADMIN (Master Administrator)
--------------------------------------------------------------------------------
Purpose: Business owners, CFOs, and head platform administrators.
Access Level: Unrestricted, platform-wide read, write, update, and delete access.

Key Capabilities:
  - System Governance: Create new user accounts, assign roles, deactivate users, 
    and perform emergency password resets.
  - Financial Visibility: Full access to revenue charts, gross profit trends, 
    Cost of Goods Sold (COGS), purchase bills, and batch supplier costs.
  - Soft-Delete & Purge Control: Exclusive authority to soft delete orders, 
    view the Trash Bin, restore orders, or permanently wipe trashed records.
  - System Settings: Configure company profile, currency symbol (Rs. / INR), 
    dead stock threshold days, and global inventory rules.
  - Integrity Auditing: Run system-wide stock reconciliation audits to detect 
    any variance between physical batch counts and central ledger quantities.

--------------------------------------------------------------------------------
4.2 STAFF (UpVolt Central Operations Staff)
--------------------------------------------------------------------------------
Purpose: Central warehouse operators, packaging staff, and procurement officers.
Access Level: Central catalog, warehouse stock inwarding, and order management.

Key Capabilities:
  - Catalog Management: Add new hardware components, edit specs, update categories.
  - Stock Inwarding: Record supplier purchases, add batch quantities, barcodes.
  - Order Fulfillment: Create customer orders, draft quotes, reserve stock, 
    generate invoice slips, and mark orders as Dispatched/Delivered.
  - College Distribution: Package and initiate stock dispatches to college nodes.
  - Returns Handling: Inspect returned hardware and restock into inventory.

Restrictions:
  - NO access to gross profit margins, revenue totals, or profit trends.
  - CANNOT delete users or alter global system settings.
  - CANNOT delete commercial orders (can only cancel or mark returned).

--------------------------------------------------------------------------------
4.3 COLLEGE_MEMBER (College Campus Lead)
--------------------------------------------------------------------------------
Purpose: Student chapter leads or faculty representatives at affiliated colleges.
Access Level: Strictly scoped to their designated institution (e.g. IIT Bombay).

Key Capabilities:
  - Campus Stock Ledger: Real-time visibility into parts stored in campus lab.
  - Received Shipments: Inspect and acknowledge hardware dispatches received 
    from UpVolt Central Warehouse.
  - Campus Fulfillment: Monitor local campus deliveries and stock distribution.

Restrictions:
  - CANNOT view Central Warehouse total quantities or other colleges' stock.
  - CANNOT view supplier purchase bills, pricing histories, or platform finances.
  - CANNOT access central customer list, settings, or user administration.

--------------------------------------------------------------------------------
4.4 CAMPUS_EXECUTIVE (Campus Delivery / Handover Agent)
--------------------------------------------------------------------------------
Purpose: On-ground campus delivery representatives delivering kits to students.
Access Level: Mobile-optimized, single-purpose interface for student delivery.

Key Capabilities:
  - Campus Delivery Queue: View list of student orders waiting for pickup/delivery.
  - Search: Quickly find student records by Student Name, Phone, or Order ID.
  - Handover Confirmation: Mark package as successfully handed over to student 
    with one click, updating the delivery timeline in real time.

Restrictions:
  - Entirely locked out of Central Warehouse, Inventory, Purchases, Catalog, 
    Finance, Reports, Settings, and User Management.

5. INVENTORY & FINANCIAL BUSINESS INVARIANTS (FIFO ENGINE)
================================================================================

UpVolt Manager runs on a strict First-In, First-Out (FIFO) inventory core to 
comply with Indian Accounting Standards and prevent inventory value drift.

1. Batch Inwarding:
   Every time stock is purchased, a unique `InventoryBatch` is generated:
     - `batchNumber` (e.g. BATCH-2026-0001)
     - `unitCostPrice` (exact purchase rate per piece)
     - `receivedQuantity` (original count)
     - `remainingQuantity` (unconsumed count available)
     - `status`: ACTIVE | DEPLETED

2. FIFO Consumption Rule:
   When an order is confirmed/dispatched:
     - The FIFO engine queries the oldest active batches (`receivedDate ASC`).
     - Stock is consumed atomically via `$inc: { remainingQuantity: -takeQty }`.
     - Cost of Goods Sold (COGS) is calculated dynamically from actual batch costs.
     - Profit = (Selling Price - Weighted FIFO Unit Cost) * Quantity.

3. Non-Negative Inventory Invariant:
   Available Stock = (Physical Stock - Reserved Stock).
   Orders cannot be confirmed if available stock is insufficient. No negative 
   quantities are permitted anywhere in the database schema.

6. STEP-BY-STEP WORKFLOW DIAGRAMS
================================================================================

--------------------------------------------------------------------------------
6.1 Hardware Procurement & Stock Inwarding Flow (FIFO Batching)
--------------------------------------------------------------------------------

  [Supplier / Vendor]
          |
          | Delivers Hardware Shipment (e.g. 100x ESP32 @ Rs. 350)
          v
  [Staff / Admin enters Purchase Bill]
          |
          +---> 1. Create Purchase Record (Supplier, Invoice #, Payment Status)
          |
          +---> 2. Create InventoryBatch (100 units, Cost: Rs. 350, Status: ACTIVE)
          |
          +---> 3. Atomically Increment Product.currentStock (+100)
          |
          +---> 4. Generate StockMovement (Type: 'INWARD', Ref: Purchase ID)
          |
          +---> 5. Append-only AuditLog recorded with Timestamp & User ID
          v
  [Stock Available in Central Warehouse Catalog]


--------------------------------------------------------------------------------
6.2 Commercial Order Fulfillment & Auto-Costing Flow
--------------------------------------------------------------------------------

  [Customer places Order for 15x ESP32]
          |
          v
  [Staff creates Order in DRAFT status]
          |
          | Check Available Stock >= 15 ?
         / \
       NO   YES
      /       \
   REJECT      Reserve 15 units (Product.reservedStock += 15)
                |
                v
       [Order Status -> CONFIRMED]
                |
                v
       [Staff initiates Dispatch / Packaging]
                |
                v
       [FIFO Engine Invoked]
          |
          +--> Queries oldest active batches for ESP32
          |    - Batch 1: 10 units @ Rs. 320 (Depleted to 0)
          |    - Batch 2:  5 units @ Rs. 350 (Remaining: 95)
          |
          +--> Calculates exact COGS = (10 * 320) + (5 * 350) = Rs. 4,950
          |
          +--> Decrements Product.currentStock (-15) & Product.reservedStock (-15)
          |
          +--> Creates StockMovement (Type: 'OUTWARD_SALE')
          v
       [Order Status -> DISPATCHED]
                |
                v
       [Courier / Handover Completed]
                |
                v
       [Order Status -> DELIVERED] (Revenue & Gross Profit finalized)


--------------------------------------------------------------------------------
6.3 Multi-Tier College Distribution Flow
--------------------------------------------------------------------------------

  [UpVolt Central Warehouse]
          |
          | Admin / Staff creates College Dispatch (e.g. 50x Arduino Uno to IIT Bombay)
          v
  [CollegeDispatch Created: Status = 'DISPATCHED']
          |
          +---> Deducts 50x from Central Warehouse Product.currentStock
          +---> Records StockMovement (Type: 'COLLEGE_DISPATCH')
          |
          v
  [Shipment Arrives at IIT Bombay Campus]
          |
          | College Member logs into portal -> Reviews Received Stock
          v
  [College Member clicks "Accept Dispatch"]
          |
          +---> CollegeDispatch Status -> 'ACCEPTED'
          +---> Adds 50x to CollegeInventory (College: 'IIT Bombay', Product: Arduino)
          v
  [Campus Executive Portal Displays Active Student Deliveries]
          |
          | Student arrives at campus desk with confirmation ID
          v
  [Campus Executive clicks "Confirm Handover"]
          |
          +---> CollegeInventory balance decremented
          +---> Delivery marked as 'COMPLETED'
          +---> Student receives hardware; audit log recorded


--------------------------------------------------------------------------------
6.4 Order Versioning & Customer Return Flow
--------------------------------------------------------------------------------

  [Existing Order #ORD-1042 Needs Revision (e.g. Customer adds 2 items)]
          |
          v
  [Staff Edits Order]
          |
          +---> 1. System captures deep clone snapshot of original order
          +---> 2. Creates OrderVersion record (versionNumber: 1, editedBy: staff)
          +---> 3. Recalculates FIFO stock allocation & updates Order
          v
  [Full Historical Diff visible in Order Detail Modal Timeline]

  --- IF CUSTOMER RETURNS PRODUCT ---

  [Customer returns 3x defective/unused sensors]
          |
          v
  [Staff / Admin logs OrderReturn]
          |
          +---> Condition: RESTOCKABLE or DEFECTIVE?
               /          \
      RESTOCKABLE       DEFECTIVE
          |                 |
     Restock into      Marked as Scrap;
     Inventory Batch   Not added to active stock
          |                 |
          +-----------------+
          v
  [StockMovement recorded (Type: 'RETURN') + Customer Refund processed]


--------------------------------------------------------------------------------
6.5 Soft Delete & Trash Recovery Flow (Admin Only)
--------------------------------------------------------------------------------

  [Order marked for cancellation / removal]
          |
          v
  [Master Admin clicks "Soft Delete Order"]
          |
          | (Staff cannot perform this action)
          v
  [Order.isDeleted set to true, deletedAt = NOW()]
          |
          +---> Stock allocations released back to Inventory Batches
          +---> Order removed from standard Orders table
          +---> Placed in Admin Trash Bin (TrashView)
          |
         / \
        /   \
  [Restore Order]                     [Permanently Purge]
        |                                       |
  Re-evaluates stock                      Irreversibly deletes
  and restores order to active ledger     record from database


--------------------------------------------------------------------------------
6.6 Authentication & API Authorization Flow
--------------------------------------------------------------------------------

  [User Enters Username/Email & Password at /login]
          |
          v
  [POST /api/auth/login]
          |
          +---> 1. Find User by userId or email (case-insensitive)
          +---> 2. Verify account is active (user.isActive === true)
          +---> 3. Verify password via bcrypt.compare(password, passwordHash)
          |
         / \
      FAIL  SUCCESS
      /       \
  401 Invalid  Generate signed JWT (contains userId, name, role, college)
  Credentials  Return token + User Profile payload
                |
                v
  [Frontend stores token in localStorage ('upvolt_token')]
          |
          | Attached to every subsequent API request:
          | Header: Authorization: Bearer <token>
          v
  [Express authenticateToken Middleware]
          |
          +---> Decodes JWT & verifies signature
          +---> Confirms user still exists and isActive in DB
          |
          +---> [Role Gate Middlewares]:
                - requireMasterAdmin: rejects non-admins with 403
                - requireStaffOrAdmin: rejects college/exec with 403

8. PRODUCTION DEPLOYMENT & ENVIRONMENT CONFIGURATION
================================================================================

Deployment Topology (Render / Cloud PaaS):
  - Frontend: Render Static Site (Vite bundle in /client/dist)
  - Backend : Render Web Service (Node.js/Express in /server)
  - Database: MongoDB Atlas (Managed Multi-Region Replica Set)

Frontend Environment Variables (Render Static Site Dashboard):
  - `VITE_API_URL` = https://<your-backend-app>.onrender.com/api

Backend Environment Variables (Render Web Service Dashboard):
  - `PORT`         = 5002 (or 10000 per Render auto-assign)
  - `MONGODB_URI`  = mongodb+srv://<user>:<password>@cluster.mongodb.net/upvolt
  - `JWT_SECRET`   = <strong-random-256-bit-hex-key>
  - `NODE_ENV`     = production
  - `CLIENT_URL`   = https://<your-frontend-app>.onrender.com

Critical Production Checklist:
  1. MongoDB Atlas Network Access: Whitelist `0.0.0.0/0` (Allow from Anywhere) 
     so dynamic cloud container IPs can establish database connections.
  2. Single Page App (SPA) Rewrites: Configure Render Static Site rewrite rule:
     Source: `/*`  -->  Destination: `/index.html` (Action: Rewrite).
  3. Default Master Admin: Seeded automatically on initial boot with:
     Username: `admin` | Password: `Admin@12345`.
